# Pstack 代码净化与去噪检查表 (/unslop Checklist)
## Anti-AI-Slop Code Hygiene Standard

大模型写代码最典型的通病是产生大量的“AI 垃圾（AI Slop）”——过度抽象、无意义的废话注释、满屏脆弱的防御性检查以及投机性套娃。在向用户提交任何代码变更前，必须对照本检查表逐项自查并清洗。

---

## 🚫 一、 必须清除的 AI Slop 典型模式

| 模式名称 | 典型不良代码表征 | 净化原则与正向动作 |
| :--- | :--- | :--- |
| **口水废话注释 (Obvious Comments)** | `// Iterate through users`<br>`for (const user of users) {` | **彻底删除**。只保留解释“为什么（Why）”这样写的架构原因与边界背景，绝不写解释“做了什么（What）”的废注释。 |
| **过度包装套娃 (Premature Abstraction)** | 只有一个调用的地方，却定义了 `UserProcessingStrategyFactoryImpl`。 | **压平扁平化**。就地编写内联函数或简洁的纯函数，遵循先减后加原则。 |
| **防御性蔓延 (Defensive Sprawl)** | 在强类型（TypeScript/Rust）已经保证非空的情况下，依然层层写 `if (!user) return null;`。 | **信赖类型系统**。在系统 I/O 边界完成反序列化校验后，内部逻辑直接消费强类型对象，删除多余死代码。 |
| **异常静默吞没 (Silent Catch Swallowing)** | `try { ... } catch (e) { /* ignore */ }` 或只打印 `console.log(e)` 强行返回默认空值。 | **直面真实错误**。让错误在源头暴露并传递有意义的上下文堆栈，严禁掩耳盗铃。 |
| **复读机式注释 (Echoing Comments)** | 在代码中注释 `// As requested by user, we change timeout to 5000`。 | **清除对话痕迹**。代码是生产级长期资产，严禁将 Prompt 提示词的碎片残留写入正式源码。 |
| **假大空防御性重构 (Unnecessary Decoupling)** | 借口“解耦重构”，擅自把本来只有 20 行的干净模块拆成 5 个文件。 | **守住简单性**。坚持单文件内聚原则，直到物理规模证明拆分必要性为止。 |

## 📋 二、 /unslop 代码出厂自查六问

在通过 `review_diff_in_vscode` 呈报代码或打勾前，Agent 必须在内心回答这 6 个问题：

- [ ] **Q1. 每一条新增的注释都无法用更清晰的代码命名替代吗？**  
  （若改用自解释的变量/函数名就能看懂，立刻删掉该注释）
- [ ] **Q2. 当前代码中是否存在“仅在未来某种假设下才有用”的额外入参或分支？**  
  （若有，立刻依据杜绝投机性抽象原则砍掉）
- [ ] **Q3. 当前改动的文件行数是否达到了解决目标问题的理论极限最小值？**  
  （消除任何无关的空行、格式化抖动或顺手微调）
- [ ] **Q4. 是否在类型系统已经提供安全保证的前提下，堆叠了无意义的运行时防御代码？**  
  （若类型系统已保障，立刻剔除冗余 `null` 校验）
- [ ] **Q5. 错误处理是否清晰明确，没有将关键异常吃掉或替换成模棱两可的假数据？**  
- [ ] **Q6. 这段代码读起来像是一位经验丰富、惜字如金的资深工程师写的，还是像语言模型吐出的模板样板？**  

---

## 🧼 三、 自动净化执行指令

当用户或流程显式调用 `/unslop <file-path>` 时，Agent 必须以“只读审查 + 净水修剪”模式运行：
1. 读取目标文件的当前 `git diff`；
2. 识别上述 6 类典型 Slop 模式；
3. 输出纯粹修剪后的精炼代码，并通过 `review_diff_in_vscode` 提交用户确认。
