# OrbitStack 深度审计与认知求证宪章 (Deep Audit & Cognitive Verification Charter)

> **法定地位**：本宪章为 OrbitStack (Pstack-OpenSpec) 体系应对“AI 盲目执行与浅层汇报顽疾”的最高法定审计准则。彻底终结仅凭退出码 0 或口头声称就虚假打勾的陋习，在整个工程生命周期推行**事实守恒穿透、底层结构机检、证据分级标注与独立红队对抗**。

---

## 核心痛点与行业共识

### 1. 行业共识：验证与审计是通量的唯一瓶颈
Lauren Tan (@poteto, Cursor/SpaceXAI) 明确指出：
> **“The bottleneck in AI coding isn't generating code; it is VERIFICATION.”（AI 辅助编程的真正瓶颈从来不是‘生成代码’，而是‘验证与审计’。）**  
> 如果缺乏极度严密的自动化深度审计闭环，盲目调度数十个后台 Agent，产出的只能是“规模化的代码垃圾 (Garbage at scale)”。

### 2. AI 盲目审计的四大本质病灶
1. **单维结果浅层化 (Superficial Result Bias)**：仅验证“文件是否存在”或“进程退出码是否为0”，无法感知业务事实是否被黑盒篡改、关键规程是否被静默丢弃；
2. **口头宣称与虚假自信 (Hallucinatory Confidence)**：Agent 习惯性在汇报中充斥“已严格符合要求”、“已完美优化”，却拿不出底层实测数据；
3. **缺少交叉对账机制 (Missing Cross-Reconciliation)**：无法在“源事实实体集”与“产出最终呈现”之间建立 100% 关键字/实体穿透核对；
4. **既当运动员又当裁判员 (Self-Auditing Fallacy)**：写代码的 Agent 自我审核时存在思维盲区，倾向于维护自己的修改假设。

## 一、通用深度审计四维矩阵 (The 4-Dimensional Deep Audit Matrix)

任何由 Agent 交付的工程产出，必须通过以下四维独立深度审计：

```text
┌────────────────────────────────────────────────────────────────────────┐
│                   【OrbitStack 通用四维深度审计矩阵】                    │
├────────────────────────────────────────────────────────────────────────┤
│ 维度 1: 语义事实守恒审计 (Content Fidelity & Conservation Audit)        │
│   • 目标: 严防信息被黑盒篡改或吞噬，确保“内容悉数继承源输入”          │
│   • 手段: 独立实体提取器 -> 事实交叉对账 -> 关键字穿透率必须 100%       │
├────────────────────────────────────────────────────────────────────────┤
│ 维度 2: 底层结构与 AST/OOXML 几何审计 (Structural Geometry Audit)       │
│   • 目标: 确保 100% 继承母版与框架规范，杜绝视觉畸变与布局塌方          │
│   • 手段: AST/DOM 树形遍历 -> 属性级硬断言 (对齐/缩进/边框/字体/加粗)  │
├────────────────────────────────────────────────────────────────────────┤
│ 维度 3: 业务责任与合规拓扑审计 (Legal Topology & Boundary Audit)        │
│   • 目标: 确保主体责任隔离、特殊声明上位展示与拓扑自愈保护              │
│   • 手段: 拓扑模式路由检测 -> 结构级差分比对 (Structural AST Diff)    │
├────────────────────────────────────────────────────────────────────────┤
│ 维度 4: 交付一致性与无损留存审计 (Deliverables Parity & Zero Loss)      │
│   • 目标: 黄金标本同源派生、无损留存备份与白名单差异受控                │
│   • 手段: 源文件 SHA-256 比对 -> 矩阵完整性 -> 跨主体白名单强阻断      │
└────────────────────────────────────────────────────────────────────────┘
```

## 二、四大审计核心机制与操作规程

### 机制 1：事实守恒交叉对账与穿透率门禁 (Fact Penetration Audit)
- **痛点**：源文件中有详尽的安全规程或法律声明，但被底层逻辑、正则或大模型“自作聪明”地截断、剪枝或替换为“无资料/不适用”。
- **通用审计规程**：
  1. **实体与规程前置提取**：审计脚本首先以“只读不可信模式”解析源输入，提炼出事实实体集 $E_{source} = \{e_1, e_2, ..., e_n\}$（包含操作要点、限制数值、特殊豁免条款、环境危害警示）；
  2. **交付物穿透扫描**：从编译/生成的交付物中解压、读取底层文本树，计算穿透率：
     $$\text{Penetration Rate} = \frac{|E_{source} \cap E_{target}|}{|E_{source}|} \times 100\%$$
  3. **一票否决门禁**：**穿透率必须达到 100%**。只要有任意一个关键事实丢失，审计直接报红，并精准打印出被吞噬的具体事实清单，严禁放行。

### 机制 2：底层 AST/OOXML 机器几何审计 (Machine Geometry Linting)
- **痛点**：人眼 Review 无法察觉像素级错位、两端对齐导致的非自然拉伸、制表符飞格以及跨列单元格宽度微小偏差。
- **通用审计规程**：
  1. 彻底废除“肉眼在编辑器里看一看”的假审计；
  2. 审计脚本直接解析产出物的 AST / XML 底层结构：
     - **对齐属性断言**：全量遍历内容节点，断言 `<w:jc>` 严格等于规范要求（如必须为 `left`，非规范节点数必须恒为 0）；
     - **缩进与制表位断言**：严格核验悬挂缩进坐标（如 420/565 dxa），严禁任何未授权制表符 `<w:tabs>`；
     - **字重与字体纯净度断言**：严格核查运行文本块，正文数值严禁加粗，字体族严格受控，杜绝外部字体污染；
     - **拓扑守恒与自愈断言**：校验跨列跨行合并属性（`gridSpan`, `tcW`），确保无悬空废弃标记（如悬空 `vMerge`）。

### 机制 3：证据等级制与真实凭证断言 (Evidence Tiering Axiom)
- **痛点**：Agent 自欺欺人，使用模糊的“已确认无误”蒙混过关。
- **通用审计规程**：
  所有审计报告与交付总结，必须对每一项结论进行严格的【证据等级标注】：
  - **`实测 (Measured)`**：具备真实的机器终端运行日志、真实的退出码 `0`、真实的 XML 节点解析输出或无头浏览器截图；
  - **`推演 (Inferred)`**：根据代码逻辑推断的可能表现，必须标黄并强制要求补充实测用例；
  - **`猜想 (Guess)`**：未经实测的假设性陈述，**属于一票否决项，严禁出现在正式交付物中**。

### 机制 4：独立红队对抗反审 (Independent Interrogation / Arena)
- **痛点**：编写业务代码的 Agent 具有确认偏误（Confirmation Bias），自我审核往往流于形式。
- **通用审计规程**：
  1. **主子 Agent 责任解耦与零信任**：施工 Agent 只负责编写与单点自测；主 Agent 或专门的 Audit Agent 承担独立的红队法官职责；
  2. **对抗式假设**：审查法官必须以**“假设施工者偷懒、截断了内容、破坏了既有结构”**的心态启动反审；
  3. **三不轻信原则**：不轻信口头承诺、不轻信单文件局部的绿灯、不轻信未包含在全量回归套件中的零散测试。
