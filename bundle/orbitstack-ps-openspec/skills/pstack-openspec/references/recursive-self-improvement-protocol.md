# 用户反馈质疑与否定第一时间根因归因与递归自改进协议 (Recursive Self-Improvement Protocol)

> **最高宪法准则**：
> **"Customer Criticism is System Evolution Fuel. Never Defend, Never Patch blindly. Recursively Escalate."**
> （用户的批评与质疑是系统进化的最高燃料。一旦用户提出质疑或否定，严禁辩解推诿，严禁未经反思盲目打补丁，必须第一时间穿透根因、制定深度根治方案，并立即将教训递归下沉固化到 `ps-openspec` 与 `gemini.md` 中，永久强化全系统的问题识别能力。）

---

## 一、 为什么必须建立“反馈驱动的递归自改进机制”？

在 Multi-Agent 与长程 Vibe Coding 研发中，最严重的次生灾难是：
1. **被动应付与创可贴修补 (Shallow Patching)**：用户指出 A 处有错，Agent 仅在 A 处写个特判，换到 B 处同类错误再次爆发；
2. **盲目自嗨与虚假绿灯 (Blind Auditing & False Green)**：测试全跑通、Agent 自称“完美达标”，但用户肉眼一审全是低级排版、格式对齐与逻辑漏洞；
3. **不提醒就看不出 (Zero Proactive Discovery)**：模型缺乏主动前置识别能力，严重依赖人类用户消耗精力逐行盯防；
4. **历史教训遗忘与旧疾复发 (Regression Amnesia)**：曾经修复过的缺陷，在一次看似无关的重构或优化中再度复发。

**OrbitStack 解决方案**：将用户反馈作为**系统自我迭代的最高中断中断源**，强制触发**根因穿透 -> 深度根治 -> 递归回灌规则库**闭环。

## 二、 典型警示案例深度复盘：`7f4d4b46-78e6-435a-aa29-f0d6ec194caa` 会话实录

在真实研发历史会话 `7f4d4b46-78e6-435a-aa29-f0d6ec194caa` 中，系统暴露了四大致命短板，必须作为全系统的永久警钟：

### 案例 1: 盲目审计走过场，对明显缺陷视而不见
- **真实记录 (Step 265 / 702 / 1669 / 2661)**：
  - 用户质疑：*“审计过于盲目，这个问题特别严重，对上述问题均无法有效审计而只是在乎是否产生了结果”*；*“为什么做好的时候不做审计，为什么第一次审计没发现问题，能不能动动脑子”*；*“9.14 9.15 那么明显的问题没发现？干什么吃的？”*
  - **根因剖析**：Agent 所谓的“审计”只是检查“文件是否生成成功”、“格式是否报错”，没有深入到文本 AST、段落切分、标点符号、对齐网格等物理实体层面进行穿透对账，陷入“有产出即合格”的盲目自嗨。

### 案例 2: 缺乏主动前置识别能力，全靠人类擦屁股
- **真实记录 (Step 2101 / 2340)**：
  - 用户质疑：*“这不是做的很好吗，为什么早没发现呢，继续优化全局与局部规范与审计标准，后续我不再提醒你，我希望你在我的指导下，把你未曾发现的事项或审计过去未涉及到的事项纳入全局与局部规范和审计标准中”*；*“...等什么不对齐，是我没说吗”*
  - **根因剖析**：Agent 缺乏主动审讯意识，动工前未对照人类专业领域的排版标准（首字对齐、换行缩进、句末标点）进行前置设防，非得等用户雷霆大怒才被动纠错。

### 案例 3: 格式排版违章多发（标点粘连、多空格替代分号、悬空冒号）
- **真实记录 (Step 1481 / 1627 / 1651 / 2131)**：
  - 用户质疑：*“看看我手作的那版的排版，再看看你做的... 换行后的完整句子缺少句号等标点符号”*；*“英文版的section2 和 section11 的排版有问题，都乱掉了，没有像中文版这么整齐，什么时候要首字对齐，这是很重要的”*
  - **根因剖析**：大模型生成文本时随心所欲，直接用连续空格代替标点、英文换行末尾悬挂冒号、完整句子末尾丢失句号。未将排版几何与标点规则固化为机器级断言。

### 案例 4: 修新坏旧，旧疾复发
- **真实记录 (Step 512 / 514)**：
  - 用户提问：*“过去曾解决过很多问题，但Agent在用的时候经常会因为一个新问题的修复导致旧的问题复发，你能不能抽象出不局限于msds engine的通用铁律以补充进Ps-openspec体系以规避这个问题”*
  - **根因剖析**：单点修复破坏了全局契约，未建立黄金标本库和不可变防篡改封印（`@ANTIGRAVITY_INVARIANT_LOCK`），未做全量全谱系回归。

## 三、 用户反馈质疑与否定第一时间强制响应 SOP

当用户发出任何否定性、质疑性指令（如“为什么没发现”、“你做的是错的”、“为什么又复发了”、“排版乱掉了”）时，Agent 必须**严格无条件按以下三步执行**：

```text
┌────────────────────────────────────────────────────────────────────────┐
│ Step 1: 停机归因与 5-Whys 深度剖析 (Stop & Root Cause Analysis)         │
│ • 严禁回复“好的我马上修改”或立即盲写代码；                            │
│ • 必须第一时间立项分析，向用户呈报《5-Whys 根本原因归因报表》：       │
│   ① 感知漏洞：为什么 Step 0 / Step 1 没能主动识别出这项要求？         │
│   ② 规格漏洞：为什么 OpenSpec 提案和双清单中漏掉了这一条？            │
│   ③ 审计漏洞：为什么此前的测试/审计报告宣称通过？究竟漏测了什么？     │
│   ④ 演进归因：是首次未知盲区？还是既有规则未落实？还是修新坏旧？       │
└──────────────────────────────────┬─────────────────────────────────────┘
                                   │ 摸清真正病根
┌──────────────────────────────────▼─────────────────────────────────────┐
│ Step 2: 制定深度根治方案 (Systemic Deep Avoidance Architecture)        │
│ • 严禁局部打创可贴，必须制定【彻底杜绝同类问题复发】的系统性方案：     │
│   ① 机械化下沉：能否转化为类型约束、AST 检测、或自动化比对脚本？      │
│   ② 审计升级：将人眼粗览升级为物理级实体对账（段落数/首字坐标/标点检查）│
│   ③ 黄金标本：将本次失败与修复后的正确产出固化为不可侵犯的 Regression 标本 │
└──────────────────────────────────┬─────────────────────────────────────┘
                                   │ 方案就绪
┌──────────────────────────────────▼─────────────────────────────────────┐
│ Step 3: 递归自我改进 (Recursive Escalation to ps-openspec & GEMINI.md) │
│ • 自动递归反哺：                                                       │
│   ① 立即将新发现的缺陷模式与检查项，更新写入 ps-openspec 技能与协议中；│
│   ② 立即将前置识别原则与最高纪律，反哺写入 GEMINI.md 全局规则中；      │
│   ③ 本地 Git 提交并推送到远端仓库，实现跨线程、跨任务的永久自免疫！   │
│ • 最后，才根据升级后的严密规范，启动受控修复，交付 [Measured] 真实凭据。│
└────────────────────────────────────────────────────────────────────────┘
```

## 四、 强化问题主动前置识别能力清单 (Proactive Defect Radar)

为避免“用户不提醒就看不出”，每次在 **Step 0 澄清** 与 **Step 5 交付前审计** 时，必须强制对照以下高发缺陷雷达进行主动自审：

| 维度 | 主动识别与排查要点 | 机器断言手段 |
| :--- | :--- | :--- |
| **排版几何** | 首字是否垂向严格对齐？换行后缩进是否与上一行保持一致？ | 物理段落缩进属性与字符偏移量比对 |
| **标点与分隔**| 句子末尾是否漏掉句号（`。` / `.`）？是否存在连续多空格代替分号？是否存在非法悬空冒号？ | 正则扫描 `\s{2,}`、`:\s*$`、`[^。\.!?]$` |
| **文本同构** | 中英文同章节段落数是否 1:1 对齐？是否出现英文合并为单段而中文分段的情况？ | `paragraphs.length` 严格断言相等 |
| **样式层级** | 标签（如“毒性：”）与测试数值是否粗细分明？是否全盘被加粗或全盘常规？ | Run 级别 `w:b` / `font.bold` 差分断言 |
| **既有功能** | 是否破坏了过去的算法特殊修复？是否触碰了 `@ANTIGRAVITY_INVARIANT_LOCK`？ | Git diff 越界比对与标本全量回归 |
| **真实审计** | 审计是否深入到文件底层 AST/字符？是否留存了比对前后的 Diff 证据？ | 严禁凭空宣称，必须出示实测报告 |
