# Gate 1: 需求全量对账备忘录 (`multi-agent-spawn-approval-and-role-dispatch`)

## 1. 原始用户指令（100% 逐字留存 · 事实指纹）
> 「以后，任何线程没我允许禁止开新Swarm或Subagent，所有需要开设的必须单独向我请示！优先复用已有相关职能智能体，所有Agent（含Subagent）必须赋予职能标签与详情，并按照职能来赋予任务；参考下poteto的多Agent架构思路」

## 2. 1:1 需求物理对账矩阵 (RTM)

| 需求 ID | 原始需求拆解 | 场景故事 (Scenario Story) | 详细功能契约 (Functional Contract) | 独立验收指标 (Acceptance Criteria) |
|---|---|---|---|---|
| **REQ-01** | 任何线程未经用户明确允许禁止开设新 Swarm 或 Subagent | 作为全局会话与算力资源的最终决策者，我希望在任何线程、任何任务中，Agent 均不得擅自静默拉起新的 Swarm 成员或 Subagent；只要确需新设，必须单独向我发起请示并获得批准后方可执行。 | 在最高宪法层与调度门禁中确立“零擅自开设”硬规则：任何新开 Swarm 或 Subagent 前，必须向用户单独请示（说明拟开设数量、理由、职能与成本），未获用户明确批准时物理阻断拉起动作。 | 全局规范与静态守卫中均明确包含“未经用户明确许可禁止新开 Swarm/Subagent”及“单独请示门禁”条款与对应机械校验，相关单元测试通过（Exit Code 0）。 |
| **REQ-02** | 优先复用已有相关职能智能体 | 作为希望控制上下文碎片与智能体膨胀的协调者，我希望当需要某类专业能力时，系统首先检索并复用当前线程或团队中已经存在的对应职能智能体，仅在无匹配或不可复用时才向我请示新开。 | 调度流程必须强制执行“先盘点现有活跃/空闲智能体台账 -> 按职能匹配复用 -> 确实缺失才发起新开请示”的顺序，禁止跳过复用检查直接请求新开。 | 规范与调度校验逻辑要求“先复用已有同职能智能体，无匹配再单独请示”，并可通过测试用例验证违规跳过复用会被阻断。 |
| **REQ-03** | 所有 Agent（含 Subagent）必须赋予职能标签与详情，并按职能派发任务 | 作为审阅多智能体协作的管理者，我希望每一个正在运行的 Agent（含 Subagent 与 Swarm 成员）都有清晰明确的职能标签（Role Tag）与职能详情（Role Spec/Scope），且后续派发给它的任务必须严格匹配其职能边界，不允许跨职能乱派。 | 每个 Agent 实例注册/请示时必须携带结构化的 `roleTag`（职能标签）与 `roleDetail`（职能详情/职责边界），任务派发前必须校验目标任务与该 Agent 职能的契合度，禁止将非对应职能任务硬塞给已锁定职能的 Agent。 | 调度校验器对缺失 `roleTag` / `roleDetail` 或跨职能错配派发的记录予以阻断，且所有宪法镜像与 Worker 规范对齐一致。 |
| **REQ-04** | 参考并融合 poteto（Lauren Tan）的多 Agent 架构思路 | 作为依托 OrbitStack/PStack 体系运作的工程师，我希望上述多 Agent 治理机制不是拍脑袋的孤立规则，而是深度对齐上游 `pstack-upstream` 中 poteto 的多 Agent 架构原则（如专业化角色分工、显式交接契约、主协调裁决权隔离等）。 | 在 Step 1 底座感知阶段系统性核查 `pstack-upstream` 中 poteto 关于多 Agent 协同的原生原则与剧本，将其角色分工、职责边界与协调控制模式融入本次治理规范。 | 最终落地的规范与架构设计明确体现对 poteto 多 Agent 架构原则的吸收与对齐，且不与现有 PStack-OpenSpec 体系冲突。 |

## 3. 前瞻性头脑风暴扩展提案清单 (Proactive Brainstorming Proposals)
- **提案 A（结构化请示卡片标准）**：统一定义“向用户请示新开 Swarm/Subagent”的标准请示格式（必须列明：为什么无法复用现有 Agent、拟新设的 `roleTag`、完整 `roleDetail`、拟分配的具体任务与预期产物），避免口水化请示。
- **提案 B（职能台账持久化与跨轮次查重）**：要求主 Agent 维护当前会话的“活跃智能体职能台账”，每次派单前先做台账检索，真正做到能复用绝不重开。
- **提案 C（职能越界自检阻断）**：当一个已有 `roleTag`（如“只读检索调研员”）的 Subagent 需要承担截然不同的新职能（如“修改核心架构代码”）时，禁止借用原壳强行派发，必须按新职能重新走复用查找或向用户单独请示。
- **提案 D（L2 机械守卫联动增强）**：将本次规则直接固化进现有的 Agent 生命周期守卫脚本与多镜像宪法一致性校验中，确保任何线程/模型都无法静默绕过。
