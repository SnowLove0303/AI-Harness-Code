# 需求澄清与对抗反审协议 (Requirements Clarification & Interrogation Protocol)

> **核心思想**：借鉴 GitHub `spec-kit`（`/speckit.specify` + `/speckit.clarify`）与 Lauren Tan `pstack`（`interrogate` + `architect`）。
> **在写下任何一行代码或创建 OpenSpec 任务前，必须消灭所有模糊地带。未澄清的需求等同于 Bug。**

---

## 一、 为什么需求理解是第一道防线？

大模型最常见的失败模式：
1. **过度顺从与自以为是**：遇到不明确的参数或边界，Agent 往往“猜一个”或“按常见套路写”，导致实现与用户真实意图产生严重偏离；
2. **缺乏契约意识**：不知道业务约束边界在哪，顺手把前人的定制逻辑改坏；
3. **任务颗粒度粗糙**：需求是一句话（“支持微信登录”），直接传给子 Agent，子 Agent 盲目发挥，结果产生大量难以合并的垃圾代码。

**OrbitStack 铁律**：**模糊输入 ➔ 对抗审讯 (/clarify) ➔ 明确契约 (/specify) ➔ 证据检查表 (/checklist) ➔ 精准下发**。

---

## 二、 需求澄清四问法 (The 4-Question Clarification Matrix)

当接收到用户的新任务需求时，必须自问并向用户发起澄清确认：

| 维度 | 审查问题 | 典型排查点 |
|:---|:---|:---|
| **1. 边界与非法状态 (Boundary)** | “哪些是非法状态？系统应该如何拒绝？” | 状态机流转边界、非法参数、未授权访问、超限输入 |
| **2. 既有契约与回退 (Preservation)** | “这个改动是否会破坏原有的特殊定制或向下兼容？” | 现有 API 签名、老版本数据迁移、特殊回退分支 |
| **3. 极限与竞态条件 (Concurrency)** | “网络超时、并发重复提交或重试时会发生什么？” | 幂等性设计、分布式锁、事务回滚、局部重试 |
| **4. 可观察性与真实验证 (Verification)** | “怎么通过命令行/接口真实证明这个需求做成了？” | 验收命令退出码、特定测试用例、断言日志、界面元素 |

---

## 三、 结构化反问工具：`/clarify` 与 `/interrogate`

在 Antigravity 中，当需求存在多项可能、技术选型或隐式假设时，**严禁自行做主**，必须主动调用交互工具 `ask_question` 或发起对抗反问：

```markdown
### 🛑 需求澄清门禁 (Clarification Gate)
在继续推进 OpenSpec Proposal 前，需要明确以下核心边界：

1. **核心场景路径**：当 [触发条件] 发生时，期望系统的最终状态是 [A] 还是 [B]？
2. **错误处理策略**：遇到不可达服务时，是就地降级重试还是立即抛出确定性异常？
3. **保持现状范围**：改动是否允许触碰 [模块X] 的既有逻辑？
```

---

## 四、 需求证据检查表 (Requirements Quality Checklist)

借鉴 `github/spec-kit` 的 `/speckit.checklist` 机制，在需求被正式签发进 `proposal.md` 与 `specs/` 之前，必须通过以下检查表：

- [ ] **无假设原则**：需求中不存在“默认认为”、“应该支持”、“大概如此”等推测字眼；
- [ ] **状态机闭环**：所有新增业务状态均在 L1 架构层或枚举中有唯一合法映射；
- [ ] **反向不变量声明**：明确写出“本需求**不做**什么”（Non-Goals）；
- [ ] **可测性指标**：每个需求点对应至少一个端到端测试用例或自动化断言命令。
