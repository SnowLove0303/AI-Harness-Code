# Pstack 对抗式代码审查协议 (/interrogate Protocol)
## Adversarial Multi-Perspective Audit Protocol

在代码编写完成、准备合入或归档（Phase 4 OpenSpec Archive）之前，Agent 必须切换身份，扮演**“极端挑剔的资深架构师 + 对抗性红队审计官（Adversarial Reviewer）”**，主动向刚刚写好的代码发起质疑与攻击，确保代码不存在暗坑或隐性退化。

---

## ⚔️ 二、 对抗式自审十问

在出具审查结论前，必须逐一自问自答：

1. **并发与竞态**：如果两个请求在微秒级同时触发该函数，会不会引发状态覆盖或死锁？
2. **极端空值**：如果下游服务返回了格式非法的数据或空对象，系统是优雅报错还是整个崩溃崩溃？
3. **副作用隔离**：这个函数是否在不该产生副作用的地方，偷偷修改了全局变量或传入的对象引用？
4. **幂等性与重试**：如果当前网络调用超时重试，会不会导致数据重复插入？
5. **既有逻辑保全**：此次修改是否破坏了未经改动的旧接口所依赖的特殊默认值？
6. **承重墙合规**：是否遵守了 AI-Harness 规定的专用引擎唯一路由（没有私自用三方库魔改底表/文档）？
7. **错误真实度**：报错信息中是否包含了充足的定位字段（如 ID、状态码、关键上下文），还是只输出了无意义的 `Error: failed`？
8. **资源释放**：所有的文件流、数据库连接、定时器和事件监听器，是否都在 `finally` 或析构函数中彻底释放？
9. **类型严密性**：是否有借用 `as any` 或 `@ts-ignore` 掩盖真实类型不匹配的逃避行为？
10. **代码异味**：是否符合 Pstack 24 原则中的“体验先行”和“最小化阅读者心智负担”？

## 📊 三、 审查结论与分流标准

对抗式审查必须给出明确的裁决报告：

```markdown
### 🛡️ /interrogate 审查审计报告

- **受审文件/Diff**：`src/order/calculator.ts`
- **攻击验证结果**：
  - [x] 极端边界测试：通过（涵盖 0 值、超大浮点数）
  - [x] 既有契约检查：通过（旧调用方入参完全兼容）
  - [x] 资源占用与性能：通过（无内存循环引用）
  - [x] 承重墙与封印：通过（未触碰 @ANTIGRAVITY_INVARIANT_LOCK）
- **裁定结论**：【绿灯通过 (APPROVED)】/【红灯驳回 (REJECTED)】
- **整改项清单**（若驳回）：
  - 缺陷 1：...
  - 整改方案：回退至 Phase 3 补全对应断言与最小修复。
```

只有在获得 **绿灯通过（APPROVED）** 后，方可推进至 OpenSpec Archive 归档与 CHANGELOG 沉淀。
