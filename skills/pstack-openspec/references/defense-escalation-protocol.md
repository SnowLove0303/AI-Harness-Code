# 防线下沉自迭代协议 (Defense Escalation Self-Iterating Protocol)

> **核心法则**：**If you correct an AI twice on the same mistake, write a linter or architectural constraint immediately.**
> （如果同一个错误你纠正了 AI 两次，立刻把它写成一条 Lint 规则或架构硬约束，绝不允许下次继续靠人眼盯防。）

---

## 1. 为什么必须自迭代？

传统的 Vibe Coding 最一致的失败模式是：
1. 程序员在 Code Review 时发现 Agent 写了错误的模式（例如：直接导入主进程模块、漏写了某个事务提交、或者使用了全局单例）；
2. 程序员在对话框里训斥 Agent，Agent 连连道歉并修改成功；
3. **下一次会话中，新 Agent 重新犯一模一样的错误**；
4. 程序员精疲力竭，信任崩塌。

Lauren Tan 体系的自迭代核心是：**将人的纠错精力，物理转化为仓库的永久防御资产**。

---

          ┌──────────────────────────────┐  ┌──────────────────────────────────┐

## 3. 防线下沉标准落地动作

### 下沉至 Layer 1（架构级）示例
- **场景**：Agent 频繁传入未经验证的订单状态字符串（如 `"PAYING"`、`"REFUNDED"`）导致越权流转。
- **下沉动作**：重构代码，引入显式有限状态机（FSM）与 TypeScript 联合类型 / 品牌类型（Branded Types），并在构造器中进行运行时断言。非法状态在编译期即报语法错误，使 Agent 无法写出非法代码。

### 下沉至 Layer 2（Linter 级）示例
- **场景**：Agent 在渲染进程组件中直接 `import electron from 'electron'` 调用主进程原生 API。
- **下沉动作**：在 `.eslintrc.js` 中增加 `no-restricted-imports` 规则：
  ```javascript
  {
    "name": "electron",
    "message": "禁止在渲染进程直接引入 electron！请通过 window.api 预加载通道调用封装好的 IPC 接口。"
  }
  ```
- **关键技巧**：**在报错 message 中必须写明正确的替代写法**！Agent 在终端执行 `npm run lint` 时看到具体指引，会在内环中自动修复。

### 下沉至 Layer 3（规则立法级）示例
- **场景**：Agent 在编写数据库迁移脚本时，总是自作聪明顺手重构原表的既有字段类型。
- **下沉动作**：在 `AGENTS.md` 的 `## 数据库演进规范` 中写入正向封闭作用域准入规则：
  - “数据库表结构变更一律采用增量加列方式，严禁就地修改、重命名或删除已上线字段；新字段必须提供默认值或允许为 NULL。”

## 4. 交付闭环凭据 (CHANGELOG 记录规范)

所有触发防线下沉的任务，必须在归档时同步更新 `CHANGELOG.md`：

```markdown
### [Self-Escalation] 缺陷固化沉淀记录
- **问题现象**：Agent 试图绕过 MSDS 引擎直改 DOCX 破坏网格几何。
- **根因分析**：模型偏向使用通用 python-docx 库走捷径，未读取架构约束。
- **下沉层级**：Layer 1 架构隔离 + Layer 2 Lint 禁令。
- **加固资产**：
  1. 在 `msds-studio` 增加源码级防篡改封印 `@ANTIGRAVITY_INVARIANT_LOCK`；
  2. 增加 ESLint 规则禁止在业务层直接引用 `docx` / `pdf-lib` 底层包。
```
