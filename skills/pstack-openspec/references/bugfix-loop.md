# Pstack 科学排错闭环标准作业规程 (Scientific Bug-Fix SOP)
## The 5-Step Pstack Bug-Fix Playbook

排错是 AI Coding 最容易导致“代码污染”、“扩大战线”与“假修复”的重灾区。Pstack 规定了不可动摇的**五步科学排错闭环**：

```text
┌────────────────────────────────────────────────────────────────────────┐
│                        【Pstack 科学排错闭环】                         │
│                                                                        │
│   1️⃣ 必须在真实环境复现 (Reproduce First)                               │
│      └─> 编写单测或最小复现脚本，终端运行抓出真实报错，严禁凭空盲修      │
│                                │                                       │
│                                ▼                                       │
│   2️⃣ 溯源探查与提出显式假设 (Investigate & Hypothesize)                  │
│      └─> 调用 /how, /why 追踪调用链，明确陈述导致 Bug 的因果物理假设   │
│                                │                                       │
│                                ▼                                       │
│   3️⃣ 验证假设与证伪立即回滚 (Falsification & Rollback)                  │
│      └─> 若假设被运行日志证伪，【立即回滚撤销所有试探性代码】，不留残渣  │
│                                │                                       │
│                                ▼                                       │
│   4️⃣ 最小微创精准修复 (Minimal Surgical Fix)                            │
│      └─> 严守最小因果集，只改动根因源头代码，绝不顺手做无谓重构          │
│                                │                                       │
│                                ▼                                       │
│   5️⃣ 原路回归与真实证据闭环 (Prove It Solved via Initial Path)          │
│      └─> 用第 1 步的完全相同命令复测，以退出码 0 与真实绿灯日志宣告闭环 │
└────────────────────────────────────────────────────────────────────────┘
```

---

## 阶段一：真实环境复现 (Reproduce First)

- **绝对禁令**：在未复现 Bug 现象前，严禁修改任何业务代码文件。
- **准入动作**：
  1. 定位触发场景，编写针对性的回归测试用例或独立的最小可复现脚本（Minimal Reproducible Example）；
  2. 运行该测试或脚本，在终端中捕获到明确的堆栈异常、断言失败或非零退出码；
  3. 将复现命令和控制台报错日志记录在思考区或 OpenSpec `proposal.md` 中，作为修复前的客观基线证据。

---

## 阶段二：溯源探查与提出显式假设 (Investigate & Formulate Hypothesis)

- **准入动作**：
  1. 使用 `/how` 向上追溯该异常值从何处产生、向下追溯在何处被消费；
  2. 使用 `/why` 检查该处逻辑当初的设计背景，确认是代码缺陷（Bug）还是前人特意设计的边界处理；
  3. **必须显式陈述物理假设**，格式范例：
     > “我假设：当入参 `amount` 为零时，由于底层除法未做非零防护，导致抛出 `DivideByZeroError`。”

---

## 阶段三：验证假设与证伪立即彻底回滚 (Falsify & Roll Back)

- **核心纪律**：
  - 如果在探查或调试修改后，发现最初的假设不成立（例如入参并不是零，或者报错原因另有隐情）：
  - **🚨 必须执行物理回滚**：立即通过 `git checkout` 或撤销编辑，还原所有试探性插入的打桩日志、临时函数或防御代码；
  - **严禁心存侥幸**：严禁保留“虽然不是这里的问题，但留着也无所谓”的试探性代码。

---

## 阶段四：最小微创精准修复 (Minimal Surgical Fix)

- **准入动作**：
  1. 直击问题第一现场根因，仅在真正产生问题的模块进行修复；
  2. 修复代码必须遵循**最小因果集（Minimal Causal Delta）**，不得发散修改无关文件；
  3. 严禁使用盲目的 `try-catch { // ignore }` 或将异常静默吞没；
  4. 检查修改区域是否触及 `@ANTIGRAVITY_INVARIANT_LOCK` 封印块；若触及，必须向用户汇报并寻求特殊授权。

---

## 阶段五：原路回归与真实证据闭环 (Prove It Solved)

- **准出标准**：
  1. **原路回归**：必须重新执行阶段一编写的复现脚本或单测命令；
  2. **结果审计**：命令必须输出真实的退出码 `0`，并且原有的报错日志彻底消除；
  3. **全仓无回归**：运行全量既有测试套件，确认未引入任何破坏性副作用；
  4. 最终证据提交：记录“修复前报错 vs 修复后绿灯”的终端日志对照，作为任务打勾打凭据。
